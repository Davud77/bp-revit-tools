# Пункт 6. Развитие MCP BotPlus RT

Спецификация к одной строке [дорожной карты](../ROADMAP.md). Дата: 11.11.2026. Статус: **план развития; новые функции ниже не объявлены реализованными**. Приёмка пользователя остаётся отдельной от статуса Codex.

## 1. Результат, которого добиваемся

Из одного MCP-подключения пользователь должен обследовать, создавать, изменять, оформлять и выпускать нативную модель Revit, а также строить её по комплекту PDF с проверяемым происхождением решений. Сложные задачи выполняются воспроизводимыми сценариями, а модель получает схемы, данные и изображения только тогда, когда они нужны.

«Ультимативный» означает измеряемое покрытие операций, достоверные результаты и меньшую стоимость успешно решённой задачи. Это не фиксированное число инструментов. Растёт полный каталог предметных операций; начальный каталог клиента остаётся компактным. Preview/apply считаются стадиями одной операции. Произвольный C#/Python, наличие метода в API или метки успеха скрипта не засчитываются как готовое покрытие.

Целевое превосходство проверяется на общей батарее задач: BP выполняет каждый подтверждённый сценарий конкурентов из согласованной матрицы, сохраняет наши более сильные защиты и проходит требования NOVA/PDF. Утверждение «лучше всех во всём» без одинаковых исходных моделей, релизов, условий и измерений не является критерием завершения.

### Исходная точка

- 151 предметное имя MCP; после добавления Code Mode — **154 в полном режиме и 5 в компактном**. Предметное покрытие при этом не выросло автоматически.
- Реализованы поиск/схемы по запросу и JavaScript QuickJS/WASM с ограничениями, общий каталог и серверный deny-list. [Описание](../modules/codex-mcp/CODE-MODE.md).
- Измерено 3584 байта JSON компактного tools/list против 127138 байт прежнего набора. Это уменьшение каталога по байтам, **не доказательство экономии токенов всей задачи**.
- В живом Revit проверено чтение через Code Mode, включая страницы. Запись через этот новый маршрут отдельно не проверялась. Остальные статусы — в [VALIDATION](VALIDATION.md).
- Сильные стороны BP: привязка плана к документу/ревизии/виду, TTL, транзакционный предпросмотр, отдельное разрешение зависимого удаления, специализированные MEP-марки и перенос ресурсов оформления.
- Основные ограничения: один фиксированный endpoint, нет публичного жизненного цикла задания/восстановления результата, нет общего контракта постусловий и составного плана. Выходные схемы есть у трёх meta-инструментов, а не у всего предметного каталога.

## 3. Целевая структура модуля

Сохраняются ключ bp_revit_ai, каталог данных BP.Revit.AI, существующие имена и единый установщик BotPlus RT. Рефакторинг идёт за совместимыми фасадами по доменам, без одновременной замены всего ядра.

| Слой | Ответственность | Необходимое отделение |
|---|---|---|
| Contracts / CapabilityCatalog | Версионированные схемы, единицы, эффекты, поддержка версии Revit, prerequisites и verification contract | Один источник для MCP, диспетчера, документации и тестовых снимков |
| Client / Code Mode | Поиск, описание, обработка данных, рецепты, управление бюджетом результата | Никаких прямых привилегий Revit API или токена в гостевом JavaScript |
| Bridge / InstanceDirectory | Обнаружение процесса и сессии, авторизация, bounded framing, совместимость протокола | Отдельно от Revit-предметных обработчиков |
| JobScheduler / OperationJournal | Очереди, backpressure, отмена, прогресс, дедупликация, status/result | Состояния транспорта не смешиваются с commit или достижением цели |
| RevitExecutor | Допуск в API context, документ, транзакции, failure handling | Revit API вызывается только из допустимого контекста |
| Domains | Datums, coordinates, walls, curtain, MEP, structure, documentation, families, parameters, exchange | Малые исполнители с явными контрактами; общие операции не копируются в каждом partial-файле |
| Verification / Evidence | Обязательные постусловия, re-read после commit, сравнение и артефакты | Непрочитанное значение не считается совпавшим |
| DocumentSession / Providers | Открытие/закрытие, локальный проект, family document; позднее APS | Сохранение/sync — отдельные эффекты с явной семантикой |
| SourceDocument / ModelIR | Разбор PDF, происхождение геометрии, согласование, diff и план модели | Извлечение данных и инженерное толкование отделены от Revit-записи |

Чистая геометрия, сопоставление, state machines и агрегация выносятся в код без зависимости от живого Revit. Адаптер Revit остаётся тонким. Новые модули не создают второй add-in manifest или отдельную пользовательскую установку.

## 4. Семь обязательных платформенных возможностей

### P01. Единый результат и доказательство выполнения

Для каждого вызова различать: принято/выполняется/завершено; commit/rollback/неизвестно; задача выполнена/частично/не выполнена/не проверена. Общий envelope содержит schemaVersion, operationId, jobId, document identity, before/after revision, warnings, errors, effect summary и ссылку на evidence.

Каждое обязательное постусловие содержит ключ, requested, actual, unit, tolerance, method, measured и verdict. Контракт задаёт полный набор ожидаемых ключей. Пустой, пропущенный, дублированный или непрочитанный check не даёт fullyVerified. Для крупных наборов возвращать число проверенных/пропущенных объектов и точную область выборки, не подменяя выборочную проверку сплошной.

Re-read выполнять после настоящего commit. Если постусловия модели не выполнены, откатывать ещё открытую внешнюю TransactionGroup и проверять статус rollback. Ошибка экспорта/сохранения после commit описывается отдельно: внешние эффекты не становятся откатываемыми от наличия группы.

Сначала покрыть параметры, стены/соседей, MEP-соединения, оси/уровни, листы и экспорт. Завести реестр verification coverage, известные ограничения и тест, запрещающий новый writer без объявленного способа проверки.

### P02. Наблюдаемые задания и восстановление ответа

Состояния: accepted, queued, waiting_revit, running, waiting_confirmation, cancelling, cancelled_before_start, completed, failed, abandoned, outcome_unknown. Изменения состояния и итог хранить в журнале с ограничением размера и времени хранения.

Ввести job_submit/status/result/cancel и progress notifications. Для медленных операций — возобновляемые стадии с checkpoint, когда Revit допускает разбиение. Очередь ограничивать глобально и по клиенту; переполнение возвращает retryAfterMs. Клиентов обслуживать справедливо, работу делить между ExternalEvent callbacks, а не опустошать всю очередь за один вызов.

Повтор с тем же operationId и тем же canonical payload возвращает прежний status/result. Другой payload с тем же ID — конфликт. Отсутствующий журнал после потенциальной записи — outcome_unknown, а не автоматическое повторное создание. Дедупликация не объявляется гарантией exactly-once через падение Revit между commit и записью журнала; такой разрыв требует сверки модели по operation markers.

Проверять разрыв соединения до старта, во время preview, до commit, после commit/до ответа и после перезапуска. Отмена после commit означает остановку продолжения, а не отмену уже записанного результата.

### P03. Несколько экземпляров Revit и явный документ

Discovery должен возвращать PID, process start identity, instanceId, версию Revit/add-in/bridge, endpoint, свежесть heartbeat и список открытых не-linked документов с session documentId. PID, имя документа или путь по отдельности не достаточны.

При нескольких целях не выбирать первый процесс. Каждая запись и план привязываются к instanceId + document session ID + revision + нужному viewId. Проверка повторяется в API context непосредственно перед изменением. Закрытие/повторное открытие файла порождает другую сессию.

Разрешены именованные каналы по instance ID либо динамический loopback endpoint с защищённым discovery. Сам выбор транспорта не является улучшением без тестов identity/ownership. Старый endpoint поддержать переходным адаптером; конфликт порта диагностировать, не завершать чужие процессы.

### P04. Составной preview/apply и один Undo

WorkflowPlan — граф типизированных операций с зависимостями и символическими результатами. Пример: трасса → реальные коннекторы → фитинги → марки. Временные ID preview не переносятся в apply; связи задаются символами, которые разрешаются заново при настоящем создании.

Единый preview репетирует весь граф в TransactionGroup с полным откатом, собирает изменения/зависимости/предупреждения/постусловия. Apply использует хеш плана, выбранную цель и текущую ревизию; один approval, одна внешняя группа, один Undo. Ошибка шага или обязательной проверки откатывает всю модельную группу.

Нельзя механически вызвать последовательность существующих preview/apply: первая запись меняет ревизию и может инвалидировать остальные планы. Нужен внутренний composable executor под общим планом.

Сохранение, sync, публикация и файлы относятся к отдельным стадиям после успешного модельного пакета; для них требуется отчёт о частичном внешнем результате, возобновление и сверка артефактов.

### P05. MEP-маршруты и соединённые сети

Первый этап: полилиния из явных точек, тип/система/уровень/форма/размер, минимальные длины, углы и уклоны. Схлопывание коллинеарных точек должно сообщаться. До записи проверять routing preferences и наличие нужных семейств фитингов; не заменять их невидимой геометрией.

После Regenerate и commit читать реальные окончания сегментов, ориентацию и профиль коннекторов, каждую пару соединений и принадлежность системе. Ось проектного поворота отличается от обрезанного фитингом конца трубы; сравнивать корректную геометрию, а не требовать невозможного совпадения.

Далее: ветвления/врезки, подключение оборудования и диффузоров, connected-run transform, изоляция, подвесы, уклоны и проверка мест обслуживания. Обход препятствий учитывает габарит с изоляцией и монтажным зазором, host/linked transforms, лимиты поиска и доступные фитинги. Различать «не найдено в заданном бюджете» и «маршрута не существует».

### P06. Параметры, аудит и выпуск

Проектные/общие параметры: GUID, spec/data type, group, категории, instance/type, значения/единицы, bindings, ReInsert/конфликты, миграция с сохранением значений. Shared parameter file — отдельный файловый эффект; временную подмену пути обязательно восстанавливать. Имя не заменяет GUID.

Аудит — версионированные наборы правил с findingId, severity, affected IDs, evidence, coverage и предложенным планом исправления. Начать с заполненности, дублей, предупреждений, семейств, видов/листов, связей и координат. Аудит не исправляет автоматически то, для чего нет однозначного проектного правила.

Пакетный выпуск: выбранный набор листов/видов, PDF/DWG/IFC/CSV/изображения, затем NWC/BCF и другие форматы по спросу. Для каждого файла проверять существование, размер, ожидаемый формат и применимые структурные признаки, сохранять hash/manifest. Проверка IFC-сигнатуры не равна проверке содержимого IFC; нужны состав, координаты и ожидаемые элементы.

### P07. Входные и выходные схемы всех операций

Сохранить старые input-контракты; добавить версионированный envelope и outputSchema с конкретными типами и единицами. Предоставлять structuredContent и совместимый text без нескольких полных дубликатов больших данных в model-facing ответе.

В manifest фиксировать read/write/file/session/network effects, поддерживаемые версии Revit и документа, prerequisite resources, max batch, output budget, verification и transaction compatibility. Генерировать справочник, примеры, JSON schemas и проверку регистрации из одного источника. Snapshot тестировать не только names/count, но required/defaults/enums, units и output schema.

Серверная policy применяется одинаково к прямому MCP, Code Mode, batch и будущим recipes. Скрыть инструмент из tools/list не означает запретить его внутреннее исполнение.

## 5. Обязательный пакет NOVA

Это требования из практической работы пользователя, а не уже закрытые задачи. Имена ниже — проектируемые контракты; окончательные имена уточняются с сохранением существующих вызовов.

### N01. Границы и представление осей

Чтение: ID/type/UniqueId, Line/Arc/MultiSegment, фактическая геометрия, нижняя/верхняя 3D-отметка с единицами и системой координат, связь ScopeBox; на выбранных видах — 2D/3D extent mode каждого конца, кривые и bubbles. Графические свойства типа и переопределения вида показывать отдельно.

Предусмотреть read_grid_extents и preview/apply_update_grids; расширить list_grids опциональными полями/детализацией, а не полным тяжёлым ответом всегда. В create_grids добавить опциональные zMinMeters/zMaxMeters, сохранив прежний сценарий.

[Grid.SetVerticalExtents](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/9c367024-cc8a-157b-6984-3883b690c474.htm) подтверждён в API 2026. Вертикальный диапазон не равен elevation линии в плане. View-specific кривую менять через допустимый DatumPlane API с проверкой совпадения исходной геометрии.

Приёмка: оси проходят заданный диапазон этажей, видимость проверена на оговорённых планах с учётом crop/view range/ScopeBox; перевёрнутые границы отклоняются; arc и multi-segment имеют отдельные тесты либо честный unsupported.

### N02. ScopeBox: чтение, назначение, точное создание

Первый подтверждаемый набор: перечисление существующих областей, ориентированный объём и transform, переименование, назначения поддерживаемым осям/уровням/видам, конфликт с шаблоном вида. Задавать явные ID и показывать несовместимые цели.

Создание/изменение произвольного XY + zMin/zMax — отдельный обязательный API spike на установленной Revit 2026. Не предполагать существование ScopeBox.Create или writable BoundingBox. В [обсуждении Autodesk](https://forums.autodesk.com/t5/revit-api-forum/create-modify-revit-scope-boxes-through-api/td-p/11838431) описаны ограничение API и обходные варианты; это не доказательство их работы во всех версиях. У shuotao исследованное действие назначает существующую область видам.

Порядок реализации: публичный API → проверенное копирование/изменение нативного образца с re-read всех 8 углов → отдельный наблюдаемый UI workflow, если API не покрывает геометрию. Перемещение копии без нужного размера не засчитывается как создание заказанного объёма. SectionBox/CropBox не выдаются за ScopeBox.

Приёмка: требуемый прямоугольный объём прочитан из нативного объекта, назначения реально работают, повтор не создаёт дубль; неподдержанный маршрут явно обозначен. До этого подпункт создания остаётся открытым.

### N03. DatumPlane на видах

Спроектировать read_datum_layout и preview/apply_configure_datums: mode на каждом конце, длины, bubbles, leader/elbow и распространение на выбранные совместимые виды.

[SetCurveInView](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/eaff0038-34f2-03cf-185b-2872cffb84af.htm) требует допустимой совпадающей кривой; нельзя просто передать произвольный отрезок. Для распространения проверять семейство/направление вида, datum visibility и ограничения шаблона.

Размещение близких высотных подписей рассчитывать в миллиметрах на бумаге с учётом текста, масштаба, heads и leaders. Приёмка: разрез с близкими уровнями без наложений; изменение 2D-представления не сдвигает физическую отметку; read-back и экспорт вида подтверждают результат.

### N04. Координаты проекта и абсолютная отметка

Читать InternalOrigin, Project Base Point, Survey Point, активный ProjectLocation, project/shared/internal transforms, true north и данные геолокации с указанием системы и единиц. Не смешивать координату точки, положение маркера и преобразование модели.

preview/apply_set_project_coordinates должен явно различать изменение системы координат и перемещение физических элементов. Опора — [ProjectLocation.SetProjectPosition](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/ff73932a-dae4-37b3-5b4d-584e4bb95e2a.htm), но поведение точек, угла и shared transforms проверяется в отдельном fixture.

Для пилота: относительный ноль соответствует абсолютной отметке 143.700 м. После применения проверить shared Z контрольной точки, обратное преобразование, истинный север, сохранность internal геометрии и связей; проверить марки абсолютных/относительных отметок. Конкретная привязка требует исходных геодезических данных, не одного числа высоты.

### N05. Пакетное изменение уровней по ID

preview/apply_update_levels: имя, elevationMeters и buildingStory; неизменные ID и сохранение связанных планов. Имена менять через временные уникальные значения, если выполняется перестановка. Высоту не сводить к общему transform без чтения зависимостей.

Preview показывает планы, хосты, верхние/нижние привязки, offset, группы и потенциальные перемещения; отдельная политика для зависимых изменений. Лимиты пакета согласовать с job slicing, а не просто снять предел 30 и заблокировать UI.

Приёмка: +3.000 → +5.700 с тем же ID уровня, сохранёнными планами и ожидаемыми зависимостями; ошибка одной обязательной записи откатывает атомарный пакет.

### N06. Синхронизация уровней и осей

read/compare → match → preview/apply_sync_datums. Сопоставление: явный mapping ID, затем однозначное имя и kind, затем геометрия с допуском только по выбранной политике. Учитывать link transform и систему координат; повторяющееся имя не разрешать по first match.

Отчёт: unchanged, create, update, rename, conflict, unsupported, extra_in_target. Удаление лишнего по умолчанию запрещено и выделяется в отдельный план зависимого удаления. Учесть дуги, reversed endpoints, наклон/зеркало связи и multi-segment.

Приёмка: повтор даёт ноль изменений; перестановка имён не создаёт дублей; конфликт одинакового имени и разной геометрии показан до записи.

### N07. Диагностика и штатное восстановление

health/doctor должны различать: процесс найден; endpoint доступен; handshake совместим; авторизация согласована; Revit модален; документ не выбран; add-in старее клиента. Не раскрывать токен, его части или хеш секрета; использовать несекретные идентификаторы эпохи авторизации и challenge-response.

Обрабатывать атомарное обновление токена и переподключение к той же instance identity; ограниченный retry только чтения и установления связи. Не повторять запись после Authentication failed/потери ответа без operation status. Не перезапускать Revit, не закрывать проект и не регенерировать секрет самовольно.

Приёмка: после штатного перезапуска Revit соединение восстанавливается; stale client получает понятную диагностику; второй процесс не подменяет первый; секреты отсутствуют в ошибках/логах.

### N08. Системные типы стен и слои

read_wall_types/read_wall_type_structure: Width, WallKind, все CompoundStructure layers с индексом, функцией, толщиной в метрах, materialId и реальным материалом; границы ядра, мембраны, wrapping, variable/structural layer, вертикально составная структура и её применимость.

Нативное создание типа планировать через дублирование подходящего системного типа и изменение допустимого CompoundStructure; не выдумывать универсальный WallType.Create. [Описание CompoundStructure](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API/files/Revit_API_Developers_Guide/Revit_Geometric_Elements/Walls_Floors_Ceilings_Roofs_and_Openings/Revit_API_Revit_API_Developers_Guide_Revit_Geometric_Elements_Walls_Floors_Ceilings_Roofs_and_Openings_CompoundStructure_html.html).

preview/apply_duplicate_wall_types и preview/apply_update_wall_types проверяют сумму слоёв/Width, функции/ядро, материалы, ограничения kind и влияние на все экземпляры типа. Missing material и совпавшее имя другого состава — конфликт; обновление используемого типа требует списка затронутых объектов.

Приёмка: тип воспроизводит заданный состав, а не только имя «660 мм»; структура читается обратно и сохраняется после reopen. Вертикально составную стену нельзя молча упростить в равномерную.

### N09. Ограничения, привязки и присоединение стен

Расширить create/update: baseLevel/baseOffset, topLevel/topOffset либо unconnectedHeight, location line (центр/ядро/грани), flip/structural, room bounding и joins. Входные режимы взаимоисключающие; выбор имени всегда разрешается в конкретный type/level ID до плана.

Attach/detach к полу/крыше выделить в операцию с API probe, проверкой допустимого host и зависимостей; не имитировать присоединение изменением высоты. Чтение показывает реальное состояние constrained/attached и непроверенные свойства.

Приёмка: изменение верхнего уровня отражается ожидаемо; выбор грани привязки не сдвигает стену неожиданно; закреплённые/групповые/stacked/профильные варианты имеют точные ограничения.

### N10. Сетки, импосты и заполнение витражей

Прямой Curtain Wall уже создаётся существующим create_walls с правильным загруженным WallKind. Не дублировать этот сценарий ради счётчика инструментов.

Добавить read_curtain_grid и preview/apply_update_curtain_grid: U/V lines и segments, offsets/angles, add/remove gridline, mullions на нужных сегментах, panel type, native curtain door panel и размеры ячеек/заполнения. [CurtainGrid.AddGridLine](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/8886680c-2075-f542-9fcd-140b8bd87d12.htm) может вернуть null; это ошибка результата, не успешное создание.

Состав операции должен учитывать зависимости при удалении линии/импоста и различие system/loadable panel. Заполнение нельзя подменять сплошной базовой стеной или произвольной дверью вне curtain host.

Приёмка: нативный витраж с проектными ВО-типами, нужной разрезкой и дверью-панелью; число/размеры ячеек, типы, оси импостов и смещения прочитаны после commit.

### N11. Стыки, LocationCurve и изменения соседей

Добавить allowJoinAtStart/End при создании, чтение flags и preview/apply_update_wall_geometry. Использовать публичные WallUtils операции по конкретному концу, применяя нужную политику до финального Regenerate. Join style (butt/miter/порядок) не смешивать с разрешением joins; доступность каждого режима проверяется отдельно.

Для каждой новой/изменённой стены capture до/после: реальная LocationCurve, placement/reference line, ориентация, join flags, габариты и затронутые соседние ID. DocumentChanged и геометрический re-read должны выявлять изменения существовавших стен, не только возвращать requested start/end вновь созданной.

Режим preserveEndpoints проверяет допуск фактических концов и непредусмотренные изменения соседей. Если Revit закрыл проектный разрыв либо удлинил стену сверх допуска, preview показывает это, apply откатывается при непредусмотренном эффекте. Возвращать фактические линии прямо из apply_create_walls.

Приёмка: два проектных разрыва по 100 мм не закрываются автоматически при запрете стыков; разрешённый join даёт ожидаемую геометрию; изменение старого соседа присутствует в evidence; Undo/reopen проверены.

Все NOVA-подпункты проверяются на копиях. Недостающие АР1.1.1 / КЖ1.1-ВНК и узлы учитываются как source gaps: инструменты не создают отсутствующие проектные сведения.

## 6. PDF → нативная 3D-модель с минимальным расходом контекста

### Пользовательский сценарий

Пользователь передаёт комплект PDF и целевой проект/шаблон. Система составляет ведомость листов, различает планы/разрезы/фасады/ведомости, извлекает геометрию и факты, показывает короткий список неоднозначностей, готовит проверяемый план и строит нативные элементы. На выходе — модель, отчёт соответствия исходникам и список неподтверждённых участков.

Один PDF не гарантирует наличия высот, слоёв конструкций и узлов. При неполном комплекте строится подтверждённая часть; предварительные допущения явно маркируются и не становятся проектными фактами. Архитектурное изображение без размеров не является полным заданием для рабочей BIM-модели.

### Конвейер и артефакты

| Стадия | Работа кода | Роль LLM | Проверяемый выход |
|---|---|---|---|
| D01 Приём | Hash файлов, страницы, metadata, вектор/растр/смешанный тип | Прочитать короткую ведомость | SourceManifest с ID и coverage каждой страницы |
| D02 Индексация | Штампы, номера/ревизии, оглавление, ссылки на узлы, viewport | Разобрать неоднозначные листы | PageIndex: sheet → viewport → purpose |
| D03 Извлечение | Векторные пути и текст с координатами; OCR только нужных растровых регионов | Анализировать выбранные фрагменты | DrawingPrimitives с источниками и OCR confidence |
| D04 Калибровка | Поворот, масштаб/единицы, контрольные размеры, page → model transform | Разрешить конфликт масштаба/опор | Calibration с невязкой по независимым размерам |
| D05 Семантика | Кандидаты стен, осей, проёмов, контуров; размеры, отметки, марки | Разрешить неоднозначность и выбрать правило | DrawingFacts: факты, provenance, unresolved |
| D06 Согласование | План ↔ разрез ↔ фасад ↔ ведомость, ревизии и секции | Рассмотреть только конфликты с evidence | ConflictSet без молчаливого усреднения |
| D07 Модель намерений | Каноническая ModelIR: геометрия, типы, связи, constraints | Оценить сводку по этажам и исключения | ModelIR со стабильными sourceObjectId |
| D08 Ресурсы Revit | Найти/сопоставить типы, материалы, семейства, уровни/оси | Решить отсутствующие/конфликтные ресурсы | ResourceMap и план недостающих типов |
| D09 Preview | Типизированный граф, пробные транзакции, prerequisites и геометрия | Просмотреть сводный diff | WorkflowPlan и preview coverage |
| D10 Построение | Нативные объекты по зависимостям, symbolic refs, checkpoints | Получать короткий прогресс | Модель и sourceObjectId → actual UniqueId |
| D11 Проверка | Re-read, наложения на планы, контрольные разрезы и количества | Проверить только расхождения/выбранные изображения | VerificationReport: checked/unmeasured/unresolved |
| D12 Обновление | Diff страниц/ModelIR и зависимых стадий, ручных правок RVT | Разрешить трёхсторонние конфликты | UpdatePlan без дублей и потери правок |

Поток: **файлы → индекс → примитивы → факты → ModelIR → ресурсы → preview → native apply → evidence**. LLM не пересылает всю геометрию обратно инструментам.

### Геометрия, единицы и достоверность

- Масштаб хранить по viewport: на одном листе могут быть 1:100, 1:20 и немасштабная схема. PDF points/pixels и координаты Revit различаются.
- Размер сопоставлять с конкретными размерными опорами. Учитывать цепи, выноски, округления, разрывы и скрытые участки. Не принимать размер штампа за размер здания.
- Проверять независимые размеры по обеим осям. Невязку цепи не распределять молча по стенам. Текстовый размер и измеренная линия при конфликте дают finding.
- Для скана оценивать поворот, перекос и растяжение. Недостоверное аффинное/перспективное исправление блокирует точное восстановление viewport.
- Этаж, отметки, толщины и location line приходят из подтверждённых фактов. Типовая высота не распространяется на другие этажи без основания.
- Различать ось, грани стены и ядра. Дуги, отверстия/острова и сложные профили не заменяются прямоугольниками без явного статуса.
- Допуск задаётся для типа элемента и качества источника до построения. Нет универсальной точности ±1 мм для любого PDF.

Для каждого объекта ModelIR хранить kind, geometry, level/host, constraints, type/material intent, source refs, confidence и unresolved fields. Provenance включает file hash, sheet/page/viewport, region/vector ID, исходную величину/единицу, transform и основание интерпретации.

Согласовывать двери/окна, отметки/пороги/подоконники, слои, лестницы, витражи, кровли, проёмы и помещения между планами, разрезами, фасадами и ведомостями. Повторяющийся этаж — подтверждённый шаблон с отличиями, а не безусловная копия. Приоритет ревизий/дисциплин определяется правилами комплекта; противоречие АР/КЖ не разрешается голосованием.

Четыре допустимых результата участка: подтверждённый нативный элемент; явно предварительный; отсутствующие сведения; неподдерживаемая операция. DirectShape/mesh допустим как обозначенный промежуточный результат, но не засчитывается вместо нативной редактируемой стены, лестницы или витража.

### Эффективное построение и повторные ревизии

Один parse каждого уникального файла; кэш по hash + версии extractor/OCR/правил/калибровки. OCR и image crops кэшируются по регионам. Неизменившийся лист не разбирается заново; зависимые факты инвалидируются при смене масштаба/координат.

Большие примитивы и выборки хранятся серверно. Сначала summary/count, затем поля/страницы по запросу. Полный PDF, JSON, mesh и повторяющиеся изображения не выдаются LLM по умолчанию. Анализ узла использует crop с контекстной привязкой; тысячу повторяющихся объектов обрабатывает код, модель видит исключения.

Порядок записи: координаты/ресурсы → уровни/оси → основная геометрия → проёмы/семейства → витражи/лестницы → помещения → виды/оформление. Размер пакета и Regenerate определяются измерениями времени UI и зависимостями. Кэш типов действителен только для нужной ревизии.

Для обновлений используются стабильные source IDs и подтверждённое геометрическое сопоставление. Хеш координаты не является единственным ID. Ручные правки дают трёхсторонний diff: старый источник → новый источник → текущая модель.

Проектируемые семейства инструментов: source_import/index/status; drawing_query/region/calibrate; drawing_extract/resolve_conflicts; model_ir_inspect/validate/compare; preview/apply_building_plan; source_model_compare; model_update_preview/apply; evidence_read/export. Тяжёлые стадии возвращают jobId/artifactId/resultHandle, counts/coverage/errors и cursor. Входной PDF не может задавать исполняемый код или команды.

### Приёмка PDF-направления

Fixtures: чистый вектор, смешанный лист, повёрнутый скан, несколько масштабов, многоэтажный комплект, дуги/сложные контуры, витражи, ревизии, неполный комплект, противоречащие размеры, повтор после ручной правки.

Сверять количество и нативные типы, оси/отметки, положение/толщины стен, проёмы/hosts, площади/контуры, этажность/constraints, витражные заполнения. Overlay — дополнительное доказательство, не замена числовой проверки. Показать coverage листов/регионов и unresolved.

Сохранение/reopen RVT, повтор без дублей и обновление без потери ручных правок обязательны. Без переданных исходных PDF это направление остаётся спецификацией, а не натурно проверенной функцией.

## 7. Покрытие всех функций Revit

### Как считать полноту

Создать реестр **нативных пользовательских операций** Revit 2026 с сопоставлением публичному API. UI-команда может требовать несколько API-вызовов; CLR-метод сам по себе не является пользовательским сценарием.

У capability: ID/domain, нативный сценарий/вариант, read/create/update/delete, inputs/outputs, units, Revit versions, API members, dependencies, implementation route, BP handler, source inspiration, fixture, known gaps и статус.

Стадии: inventoried → api_probed → implemented → contract_tested → live_tested → reopen_tested → accepted. Отдельно указывать api_supported / ui_required / blocked / unsupported, причину и следующий шаг. Наличие кода не означает приёмку.

Два знаменателя: весь согласованный реестр нативных функций и отдельно API-supported подмножество. Непокрытые UI/закрытые API не исключаются из первого ради красивых 100%.

Для пробелов: публичный API → проверенная работа с нативным образцом → наблюдаемый native command/UI workflow → явный blocker. PostCommand — постановка команды, не завершение. UI workflow имеет target identity, waiting_user, timeout/cancel и re-read; не объявляется headless-операцией.

### Расширение без переделки ядра

Descriptor и интерфейс исполнителя: read/validate/plan/rehearse/apply/verify; file/session effects выделены отдельно. Проверять уникальность регистрации и версии. Новый домен не требует менять несколько switch и создавать второй установщик.

API lookup возвращает метаданные, а не универсальный invoke. Для редких пробелов предусмотреть отдельный developer-mode проверенных C# recipes: hash/revision, входная/выходная схема, effect policy, target, transaction mode, postconditions, compile-only и отдельный dry run. Не включать его автоматически и не засчитывать за всё типизированное покрытие. JavaScript Code Mode остаётся ограничен разрешёнными MCP-операциями.

## 8. Как действительно уменьшать токены

| Механизм | Доработка | Метрика |
|---|---|---|
| Discovery | Короткий поиск, домены/эффекты, точные схемы выбранных команд, профили NOVA/MEP/docs/QA/PDF | Initial schema tokens и цена discovery |
| Детализация | summary/fields/full, каталоги enum/type/resource через handles | Избыточные схемы и ошибочные аргументы |
| Агрегаты | count/group/sum, projection, table join, spatial predicates | Raw rows против returned bytes/tokens |
| Handles | Document/session/revision/TTL-bound, paging/invalidation | Повторная передача ID и stale failures |
| Code Mode/recipes | Циклы/страницы/условия, устойчивые workflows, output budget | LLM round trips и tokens per successful task |
| Кэши | Source hash/model revision, типы, OCR/crops, стабильный prompt prefix | Cold/warm отдельно, hit rate |
| Изображения | Нужный crop/масштаб/регион, общий preview только по делу | Image input tokens и число изображений |
| Delta | Только изменённые страницы/объекты/постусловия | Повторная передача неизменных данных |
| Evidence | Крупный trace локально, детали по finding ID | Расследование при ограниченном контексте |
| Ошибки | Code/path/expected/unit и полезный next read | Ошибки, повторы, суммарная стоимость |

Батарея: большая выборка/сводка, спецификация, batch параметров, datums, стена с соседями, MEP-трасса, выпуск листов, PDF-модель и её обновление. Фиксировать модель/версию/настройки, input/output/image tokens, cached/uncached usage, round trips, tool calls, время, retries, качество и ручные исправления.

Цель: не ухудшать качество принятой задачи относительно baseline; на выбранных задачах многократного чтения снизить uncached input tokens и LLM round trips. Проценты объявлять только после одинакового воспроизводимого прогона. Маленький tools/list не оправдывает больше ошибок.

Композиция нескольких MCP-серверов остаётся функцией клиента либо отдельного оркестратора. BP execute_code не получает чужие подключения автоматически.

## 11. Критерий закрытия именно пункта 6

Пункт остаётся открытым до выполнения всех условий:

1. Capability inventory охватывает все согласованные нативные сценарии и API/UI пробелы; каждое обещанное покрытие имеет натурное доказательство.
2. P01–P07 реализованы и проверены, включая разные Revit, recovery, atomic model workflows и структурированные результаты предметного API.
3. N01–N11 закрыты на копиях моделей с проверкой геометрии, оформления, координат, зависимостей и reopen.
4. PDF-конвейер строит подтверждённую нативную модель на разных комплектах, показывает source gaps, обновляет ревизии без дублей и сохраняет ручные правки.
5. На общей батарее опубликованы качество/покрытие/input-output tokens/циклы/время. Большой каталог не ухудшает начальный контекст.
6. Продукт поставляется одним EXE BotPlus RT; сохранены контракты и данные пользователя; пройдены smoke/upgrade/rollback и приёмка человеком.
7. Если обязательная нативная функция не имеет подтверждённого маршрута, цель «все функции» не объявляется достигнутой и пункт не закрывается по числу инструментов.
